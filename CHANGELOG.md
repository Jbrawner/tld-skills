# Changelog

All notable changes to Adventure Skills are recorded here. Versions follow semantic versioning once we leave alpha.

## [Unreleased]

### Changed

- **Done now means merged.** No skill and no script in this repo may set a done-category status before the ticket's code is confirmed on the default branch; everything that used to write `Done` at commit time writes the project's **pre-merge status** instead (`In PR` by default, resolved from the tracker and never hardcoded, and simply omitted on a tracker that has no such status — a finished ticket then stays In Progress rather than being handed a substitute). This is written from an incident rather than from principle. On one project 26 tickets read `Done` while their code sat on branches that were never merged and for which no pull request was ever opened; three were still unmerged five weeks later, by then 235–238 commits behind the default branch and no longer mergeable, and nine tickets had to be reopened and rebuilt. One ticket's changelog shows the mechanism exactly: `In Progress` at 15:53:51, `Done` at 16:01:18, against a commit authored at 16:01:12 — **six seconds.** The runner that set it had `git push` and `gh` denied by design, so it could not have checked whether anything merged; it reported a status it had no way to verify, and the only reminder that a branch still owed a PR was a draft file in a gitignored directory, invisible from the tracker, from the forge, and from every other worktree. A later triage then closed the parent Stories because "all children are Done," laundering the whole thing into a clean-looking board. The fix already existed in one place — `/tld-autoland` § 1.6 has always said the ticket is not marked Done at commit time, only in § 1.8 after the merge is confirmed — so this release propagates that ordering to the rest of the family rather than inventing a new rule, and autoland's own behaviour is untouched. `/tld-pr`, `/tld-commit`, `/tld-next`, `/tld-partial-auto`, `/tld-run-test`, `/tld-side-quest`, the NPC variants, the composed `/tld-goal-handoff` goal, and the loose `~/.claude/tld-loop.sh` runner all now stop at the pre-merge status. **The human merge gate is unchanged** and is not the cause of anything here: PRs and merges stay manual, and what changed is only that the tracker stopped claiming a merge had happened when nothing had even asked for one. The new doctrine document, [docs/DONE_MEANS_MERGED.md](docs/DONE_MEANS_MERGED.md), carries the rule, the incident, the status-resolution procedure, the merge-confirmation tests and the reconciliation table; ADAPTERS.md, JIRA.md, CAMPAIGN_SCHEMA.md, CONTRIBUTING.md, STANDARDS.md and README point at it rather than restating it. Splitting `Done` from "the work is finished" split a question the skills used to ask once, so the docs now name both halves: a ticket is **work-complete** when it is Done, canceled, *or* pre-merge (what Order walks and "what's next" lookups care about), and **done-category** only when its code is on the default branch (what rollups and release claims care about). Every walk that used to skip `Done / Canceled` now skips the pre-merge status too — without that, `/tld-next` would close a ticket out and `/tld-setup` would hand the same finished ticket straight back. One exception survives, claimed by outcome rather than by label: a ticket whose realized diff is genuinely empty has nothing to merge and is marked Done directly, saying so in its output, because a manual-QA walkthrough could otherwise never be closed at all. The rule creates one new failure mode on purpose — a merged ticket that still reads pre-merge because nobody ran reconciliation — and that direction is the safe one: it understates progress, it is visible on the dashboard, and a status change fixes it.

- **`/tld-gate` is now the human-landed path's only writer of `Done`, and it fails on a tracker that lies.** A new step 4.5 tests every resolved ticket in the gated milestone against the default branch and acts on the result: a ticket that reads `Done` with its code nowhere near the default branch **FAILs the gate outright**, ahead of the regression suite, because a red test is visible and this is not; a ticket in the pre-merge status whose merge is confirmed is transitioned to `Done` in step 8, which is the only place that transition happens outside autoland; and a merge that cannot be verified is reported as unverified and blocks the hierarchy rollup without failing a green gate, mirroring autoland's rule that "I could not tell" is treated identically to "it failed." Two changes keep the gate from deadlocking against its own rule. Its completion check now accepts a ticket that is resolved **or** pre-merge, because on the human-landed path the gate runs at the milestone boundary *before* that milestone's PR merges. And the Story → Epic rollup keeps the stricter test — real `done`-category children only — so a milestone whose children are still awaiting a merge **defers** the rollup with the exact command to finish it, which is a normal outcome rather than a failure. The reconciliation section prints even when every row is clean, on the principle the audit family already uses: a check that says nothing on success is indistinguishable from a check that never ran.

- **`/tld-dashboard` reconciles the tracker against git.** It stays read-only — it reports, and `/tld-gate` writes — but it now answers the question the tracker cannot answer about itself: *is the code actually there?* A new section, printed directly under Recent Activity and never omitted when there is anything in scope, lists every Done and every pre-merge ticket with its merge verdict, its evidence, and the command that fixes it, sorted worst-first so the first row a reader sees is the one that matters. False-Done rows are repeated in the headline progress line so they survive a reader who only skims the top, and a run that caps its own scope says how many tickets it did not check, because a silently narrowed check reads exactly like a clean one.

- **The merge test is ancestry and file presence, never a commit-message grep.** Both directions of the key-grep failure were observed during the same incident and both are documented with the cases that produced them. A squash merge collapses every commit into one message, so individual ticket keys vanish from the default branch's history while the code is fully present — one PR squash-merged 76 ticket keys under a title naming none of them, and a sweep read that silence as 30 stranded tickets. In the other direction a key matches prose and substrings: one ticket "passed" because a *different* ticket's changelog narrated it, and another passed on the substring inside `XLAB-887-${Date.now()}` in a test file. The documented order is a merged PR for the ticket's own branch, then `git merge-base --is-ancestor`, then per-file presence — with the rename check that settles the four files which looked absent from the default branch and had simply been renamed on the way in, and with the rule that an absent file is strong evidence only for a file the branch *adds*, since a modified file differing proves nothing when the default branch has its own history. Anything the tests cannot settle is **UNRESOLVED** and goes to a human; it is never rounded up to merged. One tracker trap rides along because it produced this incident's headline number: `acli jira workitem search` caps at roughly 30 rows with no truncation marker, so the "30 stranded tickets" figure was the cap and not a count — pass `--paginate` on any search feeding a count, and report an unpaginated number as a floor rather than a total.

- **`tld-loop.sh` moved into the repository, at `scripts/tld-loop.sh`.** The runner driving the entire autonomous pipeline was a loose executable in `~/.claude/` with no version history, no backup and no diff anyone could review — which is a large part of why the incident above went unnoticed for five weeks: the one component that was writing false statuses was the one component nobody could read a change to. It is now tracked alongside `build-plugin.sh` and the two verify scripts, and CONTRIBUTING gains a `scripts/` section documenting all four. Installing it as a symlink (`ln -sf ~/.claude/skills/scripts/tld-loop.sh ~/.claude/tld-loop.sh`) keeps the checked-in copy and the executed copy from drifting. **This changes what can be reviewed, not what runs.** The script is a terminal entry point, not a skill: it shells out to `claude -p`, which invokes `/tld-full-auto` per ticket, and `/tld-full-auto` has no knowledge of the script and never calls it. `build-plugin.sh` packages only directories containing a `SKILL.md`, so `scripts/` is not shipped in the plugin either. Its header now says all of this in place, so the next reader does not have to infer the direction of the dependency from the call site.

- **`scripts/tld-loop.sh` gained an ending: `--pr` and `--merge`.** Without them the loop had become the driver nobody would pick — it burned tickets with the family's best properties (a fresh context per ticket, a harness-enforced deny-list on `git push` and `gh`, per-ticket budget caps) and then dead-ended at a banner telling the operator to push and PR by hand, while `/tld-goal-handoff` drove the same engine all the way to merged PRs. The flags give the loop's output somewhere to go without surrendering what makes it safe. `--pr` makes the **wrapper itself** push the branch and open the pull request — deterministic bash, no model involved, running only because the flag was passed. `--merge` (implies `--pr`) then watches CI up to a configurable ceiling (`CI_WATCH_SECS`, default 20 minutes) and merges ONLY on a positively-confirmed green result, mirroring `/tld-autoland`'s discipline point for point: the merge command's success is not believed until a `gh pr view` re-read says `MERGED`, "cannot tell" is treated identically to "it failed", a red or unconfirmable run leaves the PR open and the tickets in the pre-merge status, and a repo with no CI checks configured merges only with an explicit merged-on-local-tests-only notice. Once — and only once — the re-read confirms the merge, the wrapper marks that run's tickets Done, which satisfies the doctrine rather than bending it: with `--merge` the script *is* the thing that confirmed the merge, the same position `/tld-autoland` § 1.8 occupies. Passing the flag is the permission for that run — there is no second prompt, because the whole point of the loop is running unattended — and the inner Claude subprocesses remain hard-denied `git push` and `gh` on every path, so every outward git action stays deterministic wrapper code rather than a model's decision. A `--merge` run also preflights the lane before burning a single ticket (gh authenticated, squash allowed, write permission, resolvable default branch — the same checks `/tld-goal-handoff` composes), because discovering a dead merge lane after an hour of burns is its own small incident. Every ending is a banner that states the run's true final state: merged with tickets closed, PR open awaiting a human, CI refused, PR creation failed, or push failed with the work stranded locally — that last one being the loudest, since a silently local branch is the exact shape the original incident took. `--only`, the single-ticket smoke test, refuses to combine with the landing flags rather than silently skipping them.

- **`~/.claude/tld-loop.sh` no longer claims a merge it cannot see.** The loose, unversioned runner that produced the incident marked each ticket `Done` the moment a commit hash came back, while its own guardrails denied it `git push` and `gh` — it was structurally incapable of checking the claim it was making. It now moves each committed ticket to `$PREMERGE_STATUS` (new, defaults to `In PR`, settable in `.tld/loop.conf`), skips tickets already sitting there as well as Done ones, and reports a failed transition out loud instead of swallowing it, which the old `>/dev/null 2>&1` helper did unconditionally. The handoff is no longer a file in a gitignored directory: a run that committed anything ends with an unmissable banner naming the branch, stating plainly that nothing has merged, and giving the exact push / PR / gate commands, and the progress log opens with the same warning. The script remains untracked and outside any repository, which is its own standing risk worth deciding on separately — the file driving the entire autonomous pipeline has no version history and no backup.

- **Jira is now the framework's default issue tracker; Linear remains supported.** Nothing is removed and no campaign file needs editing — a repo with `Issue tracker: Linear` keeps working exactly as before. What changes is which path the docs and prompts present first. The canonical Tracker-resolution block now describes the skills' operation names as neutral adapter names rather than "Linear MCP tool names" and lists Jira first, `/campaign-init` and `/campaign-edit` recommend Jira in their tracker pickers, and prose that used "Linear" as a generic stand-in for "wherever your tickets live" now says "the tracker", leaving the name Linear only where a statement is genuinely Linear-specific (the `## Order` auto-link rewrite, the `sortOrder` reorder gap, the ADAPTERS.md contract). Three stale claims went with it. `/campaign-edit` still warned that Jira was **untested** and would "need some massaging", contradicting both LIMITATIONS.md and docs/JIRA.md, which have described Jira as wired end to end since it landed. README's limitation table still said downstream skills "will fail" on Jira. And `/campaign-plan`, `/milestone-create` and `/milestone-sync` hard-stopped unless the tracker was Linear, even though docs/JIRA.md already specified what each should do on Jira — with Jira as the default those three would have refused to run for most users, so each now takes the documented Jira path (milestone = Story, tickets = child Sub-tasks created in rank order; `/milestone-sync` is an explicit no-op, since there is no `## Order` text to repair). One tooling fix rides along: `scripts/verify-block-alignment.py` identified the Tracker-resolution block by the exact sentence this change edits, so after the edit it silently found **zero** embeds and stopped checking all 31 copies while still printing PASS. Its fingerprint is now an invariant sentence, which also means a file left on the old wording is still detected as drift rather than skipped.

### Added

- `/quality-sweep` skill, the fourth recurring check and the first one whose engine finds nothing at all. The other three look for a mechanical shape a parser can match: a doc that disagrees with the code, a test that cannot fail, a policy that does not hold. This one is aimed at the defects that have no shape, and no script detects a page that downloads the whole table to render four numbers, a write that half-completes and reports success, a guard that is green in the unit test and inert in production, or a help article describing a screen that was removed. A reader finds those, so the finding is done by agents: one finder per focus area in parallel, an independent verifier per candidate instructed to refute it and defaulting to refuted when uncertain, then a completeness pass asking what nobody looked at. What the engine owns instead is the half that must be deterministic, and it is the harder half, because a recurring report that reprints the same known findings every week stops being read and a real finding then hides inside the list. **One lens per run, on purpose.** A sweep that asks nine questions at once asks all of them badly and cannot be scheduled, ranked or starved independently, so each standing question is its own run, its own dated record and its own slot. Findings are stamped by **object identity**, `<lens>::<file>::<symbol>`, never by title, because the same defect re-found next week is described in different words by a different agent and a title match misses it every time. A baseline entry may use `*` in place of the lens, which is the normal case for known-open rows, since lenses overlap and a defect the performance sweep ticketed last month is the same defect the bug hunt finds this week. The status set is `NEW`, `KNOWN-OPEN <KEY>`, `SUPPRESSED <reason>` and one that exists because seeding a baseline from real tickets is lossy: **`KNOWN-FILE <KEY>`**, for a finding sharing a file with an open ticket that names no symbol. Letting a file-scoped row suppress outright would swallow a second, different defect in the same file in silence, which is the exact failure the whole skill is built to prevent, and filing them all blind would duplicate tickets, so the verdict forces the one thing that actually resolves it: read the ticket. Filing is the default rather than an offer, because the skill is built to run unattended and a finding that exists only in a transcript nobody read is a finding nobody found. Never capped: no top-N, no sampling, findings sharing one root cause folded into a single ticket, and anything left out named explicitly. **Nothing time-bound anywhere**, written into the skill and into the engine header as a rule so a later edit cannot reintroduce it: here a stale constant inverts the feature, because the de-dup then finds nothing, everything looks new, and the run duplicates every open ticket every week. Fails safe on four fronts. A failed preflight is a SKIPPED RUN, never a clean pass, and never grounds for substituting a shallower check and presenting its result as the lens's result. A `max_run_minutes` envelope becomes a printed deadline, and the engine forces `PARTIAL` by itself once it passes, so stopping early is allowed and stopping early while reporting clean is not. A repo root that is unreachable exits NOT-RUN. A baseline that was **named** and is missing or malformed exits NOT-RUN rather than being read as empty, while no baseline found by search runs degraded with everything `NEW` and a loud warning that this is a first-run baseline exercise rather than a list of emergencies. Each run also leaves a dated record in the audited repo, rendered by the engine so every lens's document comes out in the same shape rather than however that night's agent felt like writing it, and left uncommitted because an unattended run does not commit. Where lenses are ranked across scheduled slots they run in **straight rank order**: alternating them to spread the load looks fairer and is worse, since whichever slot runs dry then loses the same top-ranked lens every week, whereas straight order always loses the bottom of the list, which is the entire reason for having a ranking. A lens that keeps being starved shows up as a growing `last_completed` delta rather than as silence, which is the only way that failure is ever visible. Deliberately does **not** embed three canonical blocks, each recorded in the skill so an omission does not read as drift: **Load project config**, because it hard-stops on a missing `.tld/campaign.md` and this skill has to run in repos that have none; the **local database safety block**, because no lens writes to a database or runs a destructive command, with any project-specific database rule belonging in that project's baseline preflight next to the identity check that proves which instance is being read; and the **approval keyword set**, because filing is the default and there is no gate for a keyword to open.

- `/test-audit` skill, a recurring check that a green suite still means something. A test does not stop working the day it is written. It stops working the day the element it looked for is renamed, the day a guard is added to make it stable, the day a CI job is switched off to save minutes, and none of those raise an error: the suite keeps reporting green while the behaviour it claims to protect is broken. That failure is invisible to everything except a check that goes looking for it. Twelve checks over the whole tree, read-only and without running anything: bodies with no assertion, bodies where every assertion sits inside a conditional guard so a false guard asserts nothing and still passes, empty wait callbacks that resolve immediately, tautologies, test files no declared runner collects, CI test jobs switched off with a constant-false condition, shape-only assertions the language already guaranteed, assertions on a component's source text rather than its rendered output, skip and todo markers, conditional skips, and test files declaring no cases. The one worth understanding before triage is **`refusal-asserted-as-no-error`**: in PostgREST and several similar clients a write that row-level security refuses returns no error and changes zero rows, so `expect(error).toBeNull()` passes when the write succeeded and passes when it was silently refused, which means that assertion on a test named "prevents X from deleting Y" cannot fail. The trap runs both ways, since a positive-path test asserting only that no error came back cannot tell a successful edit from a silent refusal either. Two checks report **SKIPPED unless the baseline configures them**, printed under a heading saying it is not a pass, because an unconfigured check reading as a clean result is the same lie the skill exists to catch. Same shape as the rest of the family: project-neutral engine as a single dependency-free `.mjs` file, everything project-specific in a committed per-repo baseline, `NEW` versus `KNOWN-OPEN <KEY>` matched on object identity rather than ticket title, an object appearing only on a closed ticket filed as a regression, filing as the default rather than an offer, no cap on how many tickets get filed, nothing time-bound in any lookup, and a named-but-missing baseline exiting NOT-RUN rather than turning every tracked finding back into a new one. `config.runners` is the audit's precision and the only entry that can make it lie in both directions: a runner you forget to declare turns its whole suite into false collection findings, and a runner listed that nothing actually invokes hides real ones.

- `/docs-drift-audit` skill — a recurring documentation-versus-code check, built on the same engine-plus-baseline shape as `/rls-audit` and aimed at a different silent failure: documentation does not break loudly. A wrong price in a sales deck, a link to a file that was renamed, a schema table naming a database table that has been empty for a month — none of it turns anything red, so it survives until somebody acts on it, and by then that somebody is a customer or an agent rather than the author. The engine is one project-neutral Python file with a stdlib-only dependency set, read-only on code and on the documents themselves, and it sweeps document roots that may sit **outside** the repository entirely, because product documentation usually lives in a synced drive folder rather than in `docs/`. Six checks: an anchor whose stated value the code contradicts, an anchor whose pattern no longer matches anything (reported at HIGH as a **check gone inert**, never as a pass, which is the failure the whole design is arranged around), a baseline-named document that has left the swept set, a file path or link that resolves nowhere, a retired route or product name a document still tells readers to use, and a document whose watched code moved on well after it did. **Noise is what kills a recurring documentation check**, more so than a security one, because prose generates false positives that SQL does not: every row is labelled `NEW` or `KNOWN-OPEN <KEY>`, reviewed-safe exceptions live on an allowlist that requires a written reason per entry, and the heuristic checks over-flag on purpose with the benign shapes documented in the skill so triage is a lookup rather than an investigation. Two of those shapes are worth naming because they are counter-intuitive: a document that mentions a retired table *in order to say it is retired* must not be flagged, since the fix would delete the one sentence stopping the next reader from using it; and a whole family of unresolvable paths usually means the project writes paths from inside a subtree, which is one `path_search_roots` entry rather than fifty allowlist rows. Filing is the default rather than an offer, de-duplicated first against open tickets carrying the skill's own stable label and matched on **affected object identity** (document, anchor id, path, term) rather than ticket title, with an object appearing only on a *closed* ticket filed as a regression — the proving run produced exactly that, finding the `$29/$99` pricing a closed ticket had been closed for, still sitting in the repository's own architecture overview four months later. Never capped: no top-N, no sampling, findings sharing one root cause folded into a single ticket, and anything left out named explicitly. **Nothing time-bound anywhere**, written into the skill as a rule so a later edit cannot reintroduce it: a dated label on ticket output is fine because it is built from the real date at run time, but a date inside a lookup that has to keep matching is a check that stops matching without ever reporting that it stopped. Fails safe — an unreachable document root or an unrunnable anchor command is a SKIPPED row and a `PARTIAL` run status, never a silent green, and a missing repository or a named-but-absent baseline exits NOT-RUN rather than reporting a clean sweep of nothing. It degrades rather than fails: with no baseline at all it discovers a `docs/` directory, runs the path check, and reports everything as new. Deliberately does **not** embed three canonical blocks: **Load project config**, because it hard-stops on a missing `.tld/campaign.md` and this skill has to run in repos that have none, resolving tracker settings from its own baseline instead; **Local DB safety check**, because there is no database in scope; and the **approval keyword set**, because filing is the default and there is no gate for a keyword to open. The tree walk prunes any subdirectory carrying its own `.git`, covering linked worktrees, submodules and nested clones, because their documents are another checkout's copy of the same tree: with a `repo-root` doc root on a project that parks worktrees inside itself, descending into them swept 1,319 documents where the repository holds 151 and produced 5,378 findings where the truth was 748, each duplicate indistinguishable from a real one at triage and carrying a path that stops existing when the worktree is removed. Pruned checkouts are listed by name in the report, on the same principle as the exclusion count: a tree quietly narrowed reads exactly like a tree with nothing wrong in it.

- `/rls-audit` skill — a recurring row-level-security and SECURITY DEFINER posture check that reads the **live local database** rather than a diff. It exists because of a failure mode `/tld-audit` structurally cannot catch: `CREATE OR REPLACE FUNCTION` resets a function's grants, so a control that was correct the day it was written can be silently reverted months later by an unrelated migration, with no diff anywhere that looks wrong. The sweep that motivated this found exactly that — ten internal helpers handed back to `anon`, two of which returned cross-tenant data by UUID with no auth check at all, from a revoke that named `PUBLIC` while the grants were held by `anon` and `authenticated` by name. The two skills are complements, not duplicates: tld-audit reads the change, rls-audit reads the state. Seven checks run against the system catalogs: tables with RLS disabled, DEFINER functions without a pinned `search_path`, INSERT/UPDATE/ALL policies with no `WITH CHECK`, data-returning DEFINER helpers reachable by a client role that never authenticate, the boolean/void variant of the same, policies whose `USING` is literally `true` for a client role, and data RPCs matching the project's reporting convention that are anon-reachable or unauthenticated. **The design problem with any recurring security check is noise** — a report that reprints the same known findings every week stops being read, and a real finding then hides inside the list — so every row is labelled `NEW` or `KNOWN-OPEN <KEY>` against the ticket tracking it, and confirmed-safe exceptions live on a reviewed allowlist that requires reading the function before a name goes on it. Findings are filed to the tracker automatically rather than offered, because the skill is built to run unattended and a finding that lives only in a transcript is a finding nobody found; a de-dup pass first matches open `rls-audit` tickets on the **affected object name** rather than the title, so an unfixed hole does not collect a new ticket every run, and an object that appears only on a *closed* ticket is filed as a regression, which is the most valuable signal the sweep produces. Filing is never capped: no top-N, no sampling, no stopping once the list gets long, because a truncated security report is indistinguishable from a complete one and the gap is therefore invisible, so findings sharing one root cause are folded into a single ticket rather than dropped, and anything left out for any reason at all is named explicitly in the report. The one guard the engine infers on its own is an in-body `auth.uid()`; naming a permission helper is explicitly not enough, because a body calling `is_member(auth.uid(), x)` already counts as guarded, so any "treat these helpers as a guard" shortcut could only ever excuse `is_member(<caller-supplied arg>, x)`, which is no guard at all when an anonymous caller can pass somebody else's id, and it would turn the riskiest shape into a clean pass. Project-agnostic: the engine is one SQL file identical everywhere, and everything project-specific (schemas, client role names, reporting-RPC pattern, accepted exceptions, known-open findings, tracker) lives in a committed per-repo baseline resolved from `.tld/`, `.claude/`, or the repo root, since a repo that gitignores `.tld/` would otherwise carry an uncommitted baseline that forgets every reviewed exception between runs, with `baseline.example.sql` as the template. It degrades rather than fails: with no baseline the sweep still runs and reports everything as new, roles that do not exist in the database are ignored so plain Postgres projects work, and a repo with no tracker configured reports in full instead of guessing where to file. Deliberately does **not** embed the canonical Local DB safety check: that block resolves `Stack.Database` from `.tld/campaign.md` and exists to gate destructive operations, whereas this skill is read-only, must work in repos with no campaign file, and applies a flat loopback-only refusal instead, which is the stricter rule.
- `/tld-autoland` skill — the first and only TLD skill that merges into the default branch. Takes one small bug-fix ticket, or a chunk of them (`/tld-autoland AS-31 AS-32 AS-33`, or a Story key that expands to its children in tracker order), and drives each one end-to-end with no stops: eligibility gate → fresh branch cut from the freshly-pulled default → `/tld-full-auto` → changelog → commit → mark Done → push → open PR → watch CI → squash-merge → delete branch → back to the default branch → next ticket. One branch and one PR per ticket, so tickets never stack and a parked one never blocks the rest. Every other skill in the family stops at a verified checkpoint or an open PR by design; autoland exists for the narrow category where a review gate costs more than it protects — bug fixes you would approve without reading the diff. Because the merge gate is gone, the safety model moves from *stops* to *admission*: a ticket needs the new `auto-land` label to enter (no override flag, no approval keyword), protected surfaces are refused on both the ticket text and the realized diff, and the merge fires only on a positively-confirmed green CI result. Red checks, checks still running at the 20-minute watch ceiling, merge conflicts, required reviews, and any state that cannot be confirmed all park instead of merging — "I could not tell" is treated identically to "it failed," and auto-merge is deliberately never enabled as a consolation because an unattended merge that is never reported is the outcome the skill is built to prevent. Failures park rather than cascade: the work is committed and pushed to the ticket's own branch, the reason is posted to the ticket, the ticket is returned to Todo so exactly one is In Progress at a time (a parked ticket left In Progress makes the *next* ticket's "In Progress and assigned to me" resolution ambiguous and stalls the run), a clean default branch is restored, and the run continues to the next candidate. Nothing in the skill discards work — there is no `git reset --hard`, `checkout -- .`, `stash drop`, or `clean` on any path. A `skip`-command campaign aborts the run outright, since a merge gated on "tests green" needs tests. The final report accounts for every candidate as merged, parked, or skipped, with the diff stat and the exact resume command for anything that needs a human.
- `auto-land` workspace label (`#0EA5E9`), raising the required label set from eight to nine. It is the sole eligibility gate for `/tld-autoland` and is registered rather than left implicit for the reason recorded in the `no-tests` fix below: on Linear a label must exist in the workspace before it can be applied, so an unregistered routing key makes its path silently unreachable. Deliberately has no accepted synonym — `no-tests` accepts `build-only`, but a flow that merges into the default branch should match one exact string and nothing else. A typo fails safe (the ticket is skipped as unlabeled, never merged). Added to every reader: STANDARDS.md's canonical table and both embedders (`campaign-init`, `campaign-test`, including its Linear check list and Jira JQL audit), `campaign-validate`, README, docs/ADAPTERS.md, and docs/JIRA.md — whose routing-label note now covers both keys and their opposite failure directions.

### Changed

- Goals composed by `/tld-goal-handoff` no longer park after every ticket. Both templates (§4 multi-Story and §4b single-ticket) gain a METHOD bullet stating that a driver skill's closing "HARD STOP: you are DONE, wait for the user" is written for a human running that skill standalone and does not apply under a goal: on a clean verified checkpoint the runner lands the ticket and starts the next one without asking. The gap sat one level up from where it looked. `/tld-full-auto` already overrides its *sub-skills'* terminal stops (rule 2, "Routine forward gates are pre-approved", which identifies the go-forward option by meaning rather than slot number), but nothing overrode full-auto's **own** closing stop, so a multi-ticket goal drove ticket one correctly and then sat waiting for a user who thought the run was still going. The override is scoped rather than blanket, which matters because the failure it replaces was users hand-pasting a standing "a skill returning is NOT a turn boundary, never ask to approve a commit" preamble that also disarmed the gates worth keeping: it still binds on a HIGH audit finding, a failure the skill could not fix, drift, out-of-scope work, a non-local database, or a tracker error, and nothing under Safety is ever pre-approved. Cost is roughly 390 characters against the 4000-character `/goal` cap, so the multi-Story scaffolding now measures ~3,600 in a typical run (~3,810 with every braced clause present), leaving roughly 390 characters for the Story list rather than the ~780 quoted in the entry below, which predates this bullet. Runs beyond about ten Stories now reach for the split lever instead of a trim, and the bullet itself is on the never-trim list, since removing it to buy characters reintroduces the exact failure it fixes.
- `/npc-full` gains the same override one level down. Step 2 said to proceed directly to the commit after a green build, but never overrode `/tld-build`'s closing "do NOT invoke `/tld-run-test`, wait for the user", nor `/tld-next`'s equivalent at step 4, so the deliberately no-pause flow could pause anyway on a perfectly good build. Scoped to clean results only: `/tld-build`'s retry-cap block puts a remediation in slot 1, which is a failure rather than a routine gate, and remains covered by the existing abort rule that refuses to commit a broken build. `/tld-orchestrate` was checked and needed no change, since its outcome table already interprets sub-skill gates the way full-auto's rule 2 does and it prints no terminal stop of its own.
- `/tld-ticket` now sizes every ticket it creates. Step 4 collects a third value alongside model and effort — a point estimate — and step 6 writes it to the ticket's point field (Linear `estimate`; Jira Story Points). Points here measure **agent burn**, not human time: one point is roughly ten minutes of a single agent working the ticket alone, scaling with complexity and token cost, which is the unit that actually models throughput when the work is done by agents rather than people. Because the pipeline already decomposes work into uniform agent-sized units, the rubric biases hard to **1** — almost every sub-task `/tld-ticket` creates is a 1, a 2 is genuinely heavier work that still fits one ticket, and a 3 is usually a signal to split into pt-1 units instead (pointing at Template Rule 5, "one ticket = one thing"). Anything above 3 is Story- or Epic-sized and is handed back as a split rather than created. The skill proposes a size with a one-line rationale rather than defaulting blindly, offers the neighbouring sizes, shows the pick in the step 5 preview next to the labels, and falls back to `sonnet` + `medium` + 1 point if the prompt is dismissed. Writing the size is deliberately non-fatal: the point value is metadata while the AC, files, labels, and parent link are the payload, so a rejected write is reported and the ticket still lands.
- docs/JIRA.md gains a **Story Points (point estimates)** section covering why the Jira path needs the graceful-degradation rule above. Three facts drive it: the field id is per-instance (`customfield_10016` on many sites, not all, and some carry a legacy `Story point estimate` alongside it), so it must be resolved at call time via `getJiraIssueTypeMetaWithFields` and matched by name instead of hard-coded; the field is screen-scoped, and the usual failure on a TLD campaign is not a wrong id but Story Points being configured for Story and Epic while the work is created as **Sub-tasks**; and fixing that is a Jira project-configuration change to screens, which no skill can do at runtime. Fills the gap that made `/tld-ticket`'s new pointer to this doc a dead reference.
- `/tld-goal-handoff` now composes a **multi-Story, self-landing goal by default** instead of a single-Story goal that stopped short of a PR. No-argument runs hand off EVERY Story that still has an unfinished Sub-task, in rank order; one or more Story keys narrow the run to those Stories; a Sub-task key still composes the single-ticket goal, now via a dedicated §4b variant with NO PR gate (a mid-Story landing's PR belongs to its Story mark, not to the ticket). Each Story runs on its own branch `story/{KEY}-{slug}` cut from `origin/{default}` (worktree-safe, the same trick `/tld-autoland` uses) and ends at a **PR gate at the Story mark**: `/tld-gate` → full local suite → push → `gh pr create` → `gh pr checks --watch` with at most 3 fix-commit-push rounds on red, under a "fix the code, never the gate" rule (no editing workflows or weakening tests to force green) → `gh pr merge --squash` → confirm `MERGED` state → Story marked Done only when every Sub-task is → next Story cut from the freshly-updated default. The goal text itself carries the explicit push/PR/merge authorization, and the merge lane mirrors autoland's discipline — merge only on positively-confirmed green, "cannot tell" treated as "failed" — with one addition: a failed Story mark parks the Story (PR stays open, work pushed, reason logged) and then makes a dependency judgment, because later Stories are cut from a `{default}` that will NOT contain the parked work — Stories independent of it continue, dependent ones are skipped with a note, and the run stops entirely only when everything left depends on the parked Story. Blocked tickets still skip-and-continue within their Story. What makes "unlimited Stories" fit the 4000-character `/goal` cap: the block lists Stories, not tickets — the runner resolves each Story's unfinished Sub-tasks from Jira by rank at runtime, so the block grows ~25–35 characters per Story instead of per ticket. The rewritten scaffolding measures ~3,210 in a typical run (~3,420 with every braced clause present), leaving roughly 780 characters for the Story list, and the trim table gains a final unbounded lever: split the run into two handoffs — each Story merges at its own mark, so nothing is lost by splitting. Compose-time additions in support: a landing preflight (`gh auth status`; squash allowed and permission ≥ write via `gh repo view` — STOP with the exact remediation rather than composing a goal that dies at its first Story mark), a separately-captured Story done-transition id (Story workflows can differ from Sub-task ones), and a merge-lane guard refusing multi-Story handoffs on campaigns with no runnable test command, for the same reason `/tld-autoland` aborts skip-campaigns: no test signal to gate a merge on. Per-ticket `no-tests` labels inside a tested campaign remain fine — those tickets ride `/tld-full-auto`'s label-gated path, land with the ` — NPC` suffix, and the Story still merges on the campaign's real suite plus CI.
- Documentation now describes three routes instead of two. README's flow table gains a **TLD no-tests path** column (pipeline, what "tests" means there, what the drift check does and does not flag, trigger condition, and which skills drive it), notes that NPC refuses campaigns with a real test command, and drops the stale "same Linear tracker" framing for "Linear or Jira". `/tld-help`'s Automation table gains a row for the label-gated `/tld-full-auto` path and flags the new NPC refusal on both NPC rows. Follow-up to AS-4: the routing existed but nothing user-facing told you about it.
- The canonical "Require current ticket (strict)" block (STANDARDS.md) gains a leading **Case A0 — same-session setup context**: when the session already ran a formal `/tld-setup` whose output carries the active ticket (ID, AC, Files to Create/Modify) and nothing since indicates the ticket changed (no `/tld-next`, `/tld-skip`, `/tld-cancel`, no user statement to the contrary), phase skills use that in-conversation context and skip the redundant tracker query — cutting roughly four tracker round-trips per aggregator-driven ticket. Standalone runs without that context fall through to the existing Case A/B/C untouched. Propagated byte-identically to all ten embedders (`tld-align`, `tld-build`, `tld-commit`, `tld-partial-auto`, `tld-pr`, `tld-run-test`, `tld-skip`, `tld-write-tests`, `npc-full`, `npc-partial`); the cancel variant is deliberately unchanged since canceling may target a ticket other than the session's active one. Generalizes `tld-audit` §1's conversation-context-first pattern. (AS-10)
- `/npc-full` and `/npc-partial` now refuse campaigns with a runnable test suite (new §1a guard): before invoking `/tld-build` they resolve the test command exactly as `tld-build` step 1b does, and if it resolves to a real command (not blank, not the literal `skip`, not an `echo`-style SKIP placeholder) they stop and point to `/tld-run-test`, `/tld-partial-auto`, or a `no-tests`-labeled ticket via `/tld-full-auto`. No override keyword. Skip-style campaigns behave exactly as before. (AS-9)
- `/tld-full-auto` and `/tld-partial-auto` now claim (self-assign) the active ticket right after setup identifies it, mirroring `/tld-orchestrate` §4: unassigned tickets are assigned to the current user (Jira `editJiraIssue`/`assignJiraIssue` with the `atlassianUserInfo` accountId; Linear `save_issue`), tickets already assigned to the current user are left alone, and a ticket assigned to someone else is a STOP (claimed by another person, per docs/JIRA.md § Concurrency). Without the claim, the next phase's "In Progress AND assigned to me" resolution found zero tickets on unassigned Jira sub-tasks and broke the chain mid-run. (AS-8)
- `/tld-goal-handoff` now composes flow-aware goals instead of prescribing `/tld-full-auto` for every ticket: step 2 classifies each ticket (`full-auto` / `no-tests` / `migration`, migration wins ties), step 4's ordered list tags every entry like `AS-12 (title) [no-tests]`, the goal template tells the runner that a `[no-tests]` checkpoint reads "regression-clean, NOT spec-verified" (riding `/tld-full-auto`'s new label-gated path), campaigns with no runnable test command swap in a direct `/tld-setup` → `/tld-build` → AC-self-review method, and the landing step states the commit-suffix rules (` — TLD verified` for test-verified landings, ` — NPC` for no-test landings). Step 1 also gains a tracker guard: non-Jira campaigns stop with "tld-goal-handoff currently supports Jira only" instead of silently proceeding. (AS-7)
- `/tld-full-auto` now takes tickets labeled `no-tests` or `build-only` through a label-gated **no-tests path** instead of dying at stop condition 7: the RED phase (`/tld-write-tests`) is skipped by design (an explicit, reported skip), `/tld-build` green means the implementation is authored with no new-test requirement, and `/tld-run-test` verifies as a REGRESSION gate (existing suite must stay green; absence of new tests is not a failure and not AC-coverage drift) plus the usual file-scope drift check and manual QA plan. Mirrors the existing migration re-check pattern; if a ticket is both migration and labeled, the migration classification wins. Unlabeled tickets behave exactly as before. (AS-6)

Three defects let an over-cap block ship: hard rule 3 read "under **~4000** characters" (the tilde makes 4,300 arguable when the real behavior is that `/goal` does not run at all), step 5's pre-print self-check had four rows and length was not one of them, and step 6 asked for the character count *after* the block was already printed — so the count served as a confession rather than a gate. Rule 3 now states the hard limit and defers measurement to step 5; step 5 gains a fifth check requiring a measured count with an explicit `wc -m` on a scratch file (an eyeballed count is not a measurement, and is exactly how a 4,300-character block ships with "4,300 characters" written next to it); step 6 reframes the printed count as a receipt for a check that already passed. Follow-up to AS-4.
